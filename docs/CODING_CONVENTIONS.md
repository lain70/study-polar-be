# 백엔드 코딩 컨벤션

## 1. 기본 원칙

- Java 17에서 컴파일할 수 있는 문법과 API를 사용합니다.
- 현재 Spring Boot 2.6 및 기존 의존성 구성을 유지합니다.
- 수정 범위를 작게 유지하고 관련 없는 코드의 공백, 들여쓰기, import 순서를 바꾸지 않습니다.
- 새 코드는 주변 파일의 구조와 스타일을 따르되, 이 문서의 명시적 규칙을 우선합니다.
- 비즈니스 규칙이 불명확하면 추측해서 구현하지 않고 확인합니다.

## 2. 패키지와 계층

- 기본 패키지는 `com.polar.bear.api`를 사용합니다.
- HTTP 요청과 응답 처리는 `controllers`에 둡니다.
- 비즈니스 흐름과 트랜잭션 경계는 `service`에 둡니다.
- MyBatis 인터페이스는 `mappers`, SQL XML은 대응하는 resources 경로에 둡니다.
- 요청·응답 및 도메인 데이터 객체는 기존 `models` 또는 기능별 VO 패키지 구조를 따릅니다.
- 공통 설정은 `config`, 범용 보조 기능은 `utils`에 둡니다.
- Controller에서 SQL Mapper를 직접 호출하지 않습니다.

## 3. 명명 규칙

- 클래스와 인터페이스는 `PascalCase`를 사용합니다.
- 메서드, 지역 변수와 필드는 `camelCase`를 사용합니다.
- 상수는 `UPPER_SNAKE_CASE`를 사용하고 `static final`로 선언합니다.
- Controller는 `*Controller`, Service는 `*Service`, Mapper는 `*Mapper` 접미사를 사용합니다.
- 데이터 객체는 기존 역할에 맞춰 `*Dto`, `*Vo`, `*RequestVo`, `*ResponseVo` 형식을 사용합니다.
- boolean 이름은 의미가 분명한 `is`, `has`, `can` 계열을 우선합니다.
- 축약어보다 도메인 의미가 드러나는 이름을 사용하되, `csr`, `qna`처럼 프로젝트에서 이미 정착된 용어는 유지합니다.

## 4. 클래스와 메서드

- 클래스와 메서드는 한 가지 책임에 집중하도록 작성합니다.
- 입력 검증, 조회, 상태 변경과 응답 생성을 구분해 읽을 수 있게 구성합니다.
- 중복되는 숫자와 문자열은 의미 있는 상수로 관리합니다. 단, 기존 Public API 값은 요청 없이 변경하지 않습니다.
- null 가능성이 있는 반환값과 파라미터는 호출부에서 명확히 처리합니다.
- 단순히 값을 다시 반환하기 위한 불필요한 임시 변수는 새 코드에서 만들지 않습니다.
- 기존 코드의 광범위한 구조 변경은 별도의 리팩터링 요청이 있을 때만 수행합니다.

## 5. Spring 규칙

- 의존성은 Spring Bean으로 관리하며 직접 생성하지 않습니다.
- 신규 코드에서는 테스트가 쉬운 생성자 주입을 우선하되, 기존 필드 주입을 관련 없는 범위까지 일괄 변경하지 않습니다.
- Controller는 HTTP 상태와 응답 형식을 일관되게 반환합니다.
- 인증과 권한 검사는 기존 Spring Security 흐름을 우회하지 않습니다.
- 환경별 값과 비밀값은 `application.yml`에 직접 추가하기보다 환경 변수 또는 환경별 오버라이드를 사용합니다.

## 6. MyBatis와 데이터 접근

- Mapper 인터페이스 메서드명과 XML statement ID를 동일하게 유지합니다.
- Mapper XML의 `namespace`는 대응하는 Java Mapper의 전체 클래스명과 일치시킵니다.
- 파라미터와 결과 타입은 가능한 한 구체적으로 선언합니다.
- SQL 키워드, 들여쓰기와 동적 쿼리 스타일은 해당 Mapper XML의 기존 형식을 따릅니다.
- 사용자 입력을 문자열 치환으로 SQL에 삽입하지 않습니다.
- 데이터베이스 테이블, 컬럼, 인덱스 변경은 명시적인 요청 없이는 하지 않습니다.

## 7. 예외 처리와 로깅

- 예외를 삼키거나 성공 값으로 바꾸어 숨기지 않습니다.
- 사용자에게 반환하는 메시지와 내부 로그에 기록할 기술 정보를 구분합니다.
- 로그에는 비밀번호, 토큰, 서비스 키와 개인정보를 출력하지 않습니다.
- `System.out.println`이나 `printStackTrace` 대신 프로젝트 로거 사용을 우선합니다.
- 예외를 다시 던질 때 원인 예외를 보존합니다.

## 8. 주석과 문서

- 코드만으로 의도가 충분히 드러나지 않는 정책과 제약을 설명할 때 주석을 작성합니다.
- 코드 동작을 그대로 반복하는 주석은 추가하지 않습니다.
- 기존 주석과 TODO/FIXME는 요청 없이 삭제하지 않습니다.
- Public API 동작을 바꾸는 경우 요청 범위 안에서 관련 문서와 테스트도 함께 갱신합니다.

## 9. 테스트와 완료 기준

- 버그 수정에는 가능하면 실패 상황을 재현하는 테스트를 추가합니다.
- 테스트 클래스는 대상 클래스나 동작을 기준으로 `*Test` 형식을 사용합니다.
- 테스트 코드는 `src/test/java` 아래의 대응 패키지에 둡니다.
- 외부 DB나 Redis가 필요한 테스트는 전제 조건을 명확히 기록합니다.
- 최소 검증 명령은 `./gradlew test`이며, 실행 권한이 없으면 `sh ./gradlew test`를 사용합니다.
- 빌드 또는 테스트 실패가 기존 환경 문제인지 변경으로 인한 문제인지 구분해 보고합니다.
