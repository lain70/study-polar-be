# 로컬 상품 수정 RabbitMQ

`develop`에서 개발한 상품 **수정 API만** 대상이다. 등록 API는 기존 동기 저장을 유지한다.
DB 스키마 변경, 프론트 화면 변경, PRD 배포는 포함하지 않는다.

## 환경 분기

- `loc`만 활성: RabbitMQ 큐 접수 후 비동기 DB 저장.
- `prd` 활성: RabbitMQ 자동 설정·소비자 없이 DB 직접 저장.
- `loc,prd` 동시 활성: PRD 직접 저장 우선.
- 그 외 프로필: 직접 저장.

## 로컬 실행

이 PC에는 Homebrew로 Docker CLI, Docker Compose, Colima를 설치했다.
Python 3과 Java 17을 사용한다. 다음 명령 하나로 실행한다.

```sh
cd /Users/mac/Development/Project/polar-bear-shop-ai/polar-be
python3 scripts/run-local.py
```

Colima가 설치되어 있으면 프로젝트 전용 `polar-be-local` VM을 시작하고, RabbitMQ가
준비된 뒤 `loc` 프로필로 백엔드를 시작한다. 다른 Docker 컨텍스트를 변경하지 않는다.
Colima가 없으면 현재 Docker 엔진을 사용하며, 그 엔진은 미리 실행되어 있어야 한다.
macOS에서 JAVA_HOME을 지정하지 않았다면 설치된 Java 17을 자동 선택한다.

RabbitMQ 계정은 최초 실행 시 무작위로 생성되어 `.local/rabbitmq.env`에 저장한다.
이 파일은 소유자만 읽고 쓸 수 있고 Git에서 제외한다. 이후에는 같은 계정을 재사용한다.
`RABBITMQ_USERNAME`, `RABBITMQ_PASSWORD` 환경 변수로 직접 지정하는 것도 가능하다.
컨테이너가 이미 초기화된 뒤에는 계정 파일만 바꾸지 않는다.

기존 로컬 MySQL(3306)과 Redis(6379)는 실행되어 있어야 한다. 미실행 시 안내하고
백엔드 시작을 중단한다. AMQP 포트는 5672, 관리 UI는 http://localhost:15672이며
호스트의 루프백 주소에만 공개한다. 백엔드는 8080 포트를 사용한다.

`Ctrl+C`, 일반 종료, 시작 실패 시 RabbitMQ와 프로젝트 전용 Colima도 중지한다.
로그인 시 자동 시작하는 서비스는 등록하지 않는다. 데이터는 볼륨에 보존한다.
IDE 실행이나 직접 `sh gradlew bootRun`을 실행하면 이 자동 연동은 적용되지 않는다.

강제 종료(SIGKILL) 등으로 정리하지 못하면 다음 명령으로 전용 VM을 중지한다.

```sh
colima stop polar-be-local
```

기존에 다른 프로젝트 이름으로 수동 실행한 RabbitMQ가 있다면 먼저 해당 컨테이너를
중지해야 한다. 실행 명령은 `polar-be-local` 프로젝트만 관리한다.

## 실제 연동 검증

```sh
python3 scripts/run-local.py --verify
```

실제 RabbitMQ를 시작하고 전체 테스트와 로컬 DB 연동 테스트를 실행한 뒤 자동 중지한다.
연동 테스트는 기존 상품을 복사한 임시 상품을 큐를 통해 수정하고 DB 반영을 확인한 후
임시 상품을 삭제한다. 이력의 변경 전·후 값, 가격 변경 구분, 오래된 요청 차단, 동시 수정 및 전체 롤백도 검증한다.
기존 상품과 DB 스키마는 테스트에서 변경하지 않는다.
이 테스트는 일반 `gradlew test`에서는 건너뛰며 위 명령으로 명시적으로 활성화한다.

PRD에서는 RabbitMQ 설치나 해당 환경 변수 설정이 필요하지 않다.

## 수정 API

`PUT /api/admin/goods/{goodsNo}`, `Content-Type: application/json`.
기존 관리자 인증 토큰과 `x-auth-user-service-key`가 필요하다.
기존 상품 조회 응답을 바탕으로 등록과 같은 상품 기본정보 필드를 전송한다.
부분 수정이 아니라 기본정보 전체 교체이며, 생략한 선택 필드는 null로 저장한다.
`goodsNo`는 경로 값, 수정자는 로그인 사용자로 강제한다.
조회 응답의 `goodsInfoHistoryNo`를 수정 요청에 반드시 포함한다(양수).
번호 누락·0·음수는 400, 이미 변경된 이력 번호는 접수 전 409로 거절한다.
저장 트랜잭션에서 상품 행을 `SELECT ... FOR UPDATE`로 잠근 다음, 최신 상품 정보
이력 번호를 잠금 읽기로 조회해 요청 번호와 비교한다. 일치할 때만 상품 수정과 이력
저장을 수행한다. 일반 조회에서만 번호를 비교하고 곧바로 UPDATE하면 생기는 경쟁 조건을
방지하며, 같은 초에 일어난 변경도 각각의 이력 번호로 구분한다.
동기 저장 중 충돌도 409를 반환하며 완료 응답에는 새 `goodsInfoHistoryNo`를 포함한다.
비동기 접수 후 충돌은 소비자에서 거절되어 기존 재시도 정책 후 실패 큐로 이동한다.
충돌 시 자동으로 최신 번호를 채워 재전송하지 말고 상품을 재조회하여 변경 내용을 확인한다.
이미지 목록·파일, 등록자·등록일 및 상품 번호는 수정하지 않는다.
필수값·가격·재고·전시기간을 검증한다. 수정 시 과세 유형·배송 유형도 필수이며,
배송비는 생략할 수 없고 0 이상이어야 한다. 등록·수정 모두 문자열의 DB 컬럼 길이와
원가·판매가·할인가·배송비의 DECIMAL(15,2) 상한(9999999999999.99)을 검증한다.
상세 설명은 UTF-8 기준 65535바이트 이하, VARCHAR는 유니코드 문자 수 기준이다.
잘못된 요청은 DB 접근·큐 전송 전 400으로 거절한다.

- 로컬: 브로커의 저장 확인 후 HTTP 202, `{"goodsNo": 1, "status": "ACCEPTED"}`.
- PRD: DB 트랜잭션 완료 후 HTTP 200, `{"goodsNo": 1, "status": "COMPLETED"}`.
- 존재하지 않는 상품: 404. 검증 실패: 400. 접수/저장 실패: 500.

202는 DB 저장 완료가 아니다. 기존 GET API로 결과를 조회한다.
처리 상태 조회 API는 제공하지 않는다. 큐가 처리되지 않으면 예전 값이 조회된다.

## 실패 및 재처리

내구성 큐 `goods.update`에 영속 메시지를 전송하며 mandatory 라우팅과 publisher
confirm을 확인한다. 브로커 확인 제한은 5초다. 전송 실패 시 DB로 우회하지 않는다.
확인 타임아웃 시 메시지가 이미 접수됐을 가능성이 있으므로 무조건 재전송하지 않는다.

소비자는 단일 활성 소비자·prefetch 1로 순차 처리한다. DB 트랜잭션이 완료된 후
ACK한다. 실패 시 최대 3회 시도하고 이후 `goods.update.failed` 큐로 격리한다.
실패는 리스너 로그와 실패 큐에서 확인한다. 실패 큐는 자동 재전송하지 않는다.
재전송·재처리는 원래 `goodsInfoHistoryNo`를 유지한다. 이미 적용했거나 오래된 메시지는
최신 이력 번호와 불일치하므로 상품을 다시 갱신하지 않고 실패 큐로 격리한다.
같은 이력 번호를 가진 서로 다른 수정 요청도 한 건만 저장되므로 나머지는 재조회 후 판단한다.
요청 ID별 중복 성공 응답을 재현하는 기능은 없으며 exactly-once 전달을 보장하지 않는다. 단일 로컬 브로커 장애 시 고가용성은 제공하지 않는다.

## 상품 정보 이력과 가격 이력

두 테이블을 분리하고 상품 변경과 같은 DB 트랜잭션에서 저장한다.

- `goods_info_history`: 매 등록·수정의 가격 제외 기본정보를 JSON으로 보존한다.
  `beforeValues`, `afterValues`로 이전·이후 값을 보고 `changedFields`로 바뀐 필드를 찾는다.
  상품 정보 이력 번호, 상품 번호, 변경 유형, 변경자, 기록 시각을 함께 남긴다.
- `goods_price_history`: 원가·판매가·할인가의 변경 전·후 금액을 전용 DECIMAL 컬럼으로
  보존한다. 상품 정보 이력 번호로 같은 변경 건에 연결한다. 최초 등록과 실제 금액이
  바뀌는 수정에만 추가한다. `10`과 `10.00`은 같은 금액으로 비교한다.

정보 이력의 JSON에는 가격을 중복 저장하지 않는다. 배송비는 상품의 배송 정보에 포함되며,
별도 가격 이력의 대상 금액은 원가·판매가·할인가다. 이미지 수정은 이번 API 범위에 없다.
등록은 `CREATE`, 수정은 `UPDATE`, 기존 상품 초기 기준은 `INITIAL`로 구분한다.
가격만 변경하거나 동일한 내용을 저장해도 정보 이력 행을 추가해 수정 요청의 기준점을
갱신한다. 이때 가격 외 변경 필드가 없다면 `changedFields`는 빈 배열이다.

이력 저장이 실패하면 상품 변경도 롤백한다. 업무 코드에는 이력 수정·삭제 기능을 제공하지
않는다. 기존 DB의 가격 컬럼은 현재 값으로 유지하고 이력은 변경 추적에 사용한다.
다른 SQL 작업이 상품을 직접 수정하면 이력과 충돌 검사를 우회하므로 수정 서비스 경로를
통해 저장해야 한다.

## 이력 조회 API와 관리자 호출부

`GET /api/admin/goods/{goodsNo}/history?page=1&size=20`
기존 관리자 인증과 서비스 키를 사용한다. 응답은 다음 두 목록을 분리한다.

- `goodsInfoHistory`, `goodsInfoHistoryTotalCount`
- `goodsPriceHistory`, `goodsPriceHistoryTotalCount`

각 목록은 최신 이력 번호부터 정렬하며 page·size를 독립적으로 적용한다(size 최대 100).
상품 목록·이력 조회의 offset은 long으로 계산하며 int 범위를 초과하는 페이지는 400으로
거절한다. 페이지 1 미만·size 1 미만의 기존 보정 규칙과 size 최대 100은 유지한다.
JSON 스냅샷은 문자열이 아니라 객체, 변경 필드 목록은 배열로 반환한다.
관리자 API 모듈의 `updateAdminGoods(goodsNo, data)`는 조회한 `goodsInfoHistoryNo`를
포함한 기본정보를 전달하며, `getAdminGoodsHistory(goodsNo, params)`는 두 이력을 조회한다.
기존 관리자 화면에는 상품 수정 호출이 없으며 이번 변경으로 수정 UI를 새로 만들지는 않는다.

## 로컬 마이그레이션과 운영 적용 조건

로컬 DB에 두 이력 테이블을 생성하고 기존 상품의 현재 상태를 `INITIAL`로 보존한 뒤
`goods_info.VERSION` 컬럼을 제거했다. 이전 버전 값은 변경 내용을 담고 있지 않으므로
과거의 변경 전·후 내역을 복원할 수 없다. 초기 기록은 마이그레이션 시점의 현재 상태다.
기존 상품의 가격·재고 등 업무 데이터는 변경하지 않는다.

다른 개발 DB에서는 `src/main/resources/db/local/migrate_goods_history.sql`을 명시적으로
적용하고 상품별 초기 이력 존재 여부를 확인한다. 기존 VERSION 컬럼이 있으면 마지막에
해당 컬럼을 제거한다. 과거 `migrate_goods_version.sql`은 실행문을 비활성화했다.
신규 DB용 `docs/goods_schema.sql`에도 두 이력 테이블을 포함한다.
버전 필드만 가진 기존 큐 메시지는 자동 변환하지 않고 거절한다. 최신 상품을 조회한 뒤
새 이력 번호로 요청을 다시 구성해야 한다.

**운영 DB는 변경하지 않았다.** 이 소스는 두 이력 테이블과 초기 이력이 필요하므로
운영 배포 전에 별도 승인을 받고 마이그레이션해야 한다. PRD에서는 RabbitMQ를 사용하지
않고 DB에 직접 저장하며, 상품과 두 이력의 트랜잭션 처리는 동일하다.
